# Autonomous Handoff Ops Design

日期：2026-04-11

## 目标

为当前知识库增加一层可长期自动运行的操作结构，使 Codex 可以：

- 持续处理工作板中的工作
- 不因小步骤完成而频繁停下
- 只在“自然阶段交接点”停下
- 且这个停止点必须由验证驱动，而不是主观感觉驱动

## 核心原则

### 1. 停止权交给验证

交接不是“做了一批事”就发生，而是“做完一批已经被验证到位的事”才发生。

### 2. 工作内容与运行协议分离

- 工作板定义“做什么”
- runbook 定义“怎么连续跑”

### 3. handoff 只记录自然停止点

`handoff.md` 不做叙述性日记，只记录：

- 本轮完成了什么
- 什么已验证通过
- 为什么现在应该停
- 下一轮从哪里继续

### 4. 高风险问题优先交接

如果继续推进会跨越：

- 高风险
- 高成本
- 不可逆
- 需人类裁决

则必须提前进入 handoff，而不是继续自动推进。

## 文件结构

推荐结构：

```text
ops/
  charter.md
  workboard.md
  runbook.md
  handoff.md
```

### `ops/charter.md`

长期宪章。定义：

- 项目目标
- 仓库边界
- 允许和禁止事项
- 默认质量标准
- 什么算“有价值工作”
- 哪些事情必须交给人类裁决

### `ops/workboard.md`

当前阶段工作板。定义：

- 当前阶段
- 工作项
- 优先级
- 依赖
- 每个工作项的完成定义
- 每个工作项的验证方式

### `ops/runbook.md`

自动运行协议。定义：

- 启动时读哪些文件
- 默认循环
- 什么时候必须验证
- 什么时候可以继续
- 什么时候必须交接
- 什么叫自然停止点

### `ops/handoff.md`

交接包。只记录最新一次可恢复状态：

- 交接类型
- 当前阶段
- 已完成内容
- 已通过验证
- 未决风险
- 下一步建议
- 下次启动点

## 自然停止点定义

当前仓库默认采用：

> 只有当当前阶段目标已经完成到足以通过既定验证标准，并且继续运行会进入下一阶段或需要新的判断时，才进入交接。

这意味着：

- 一个工作项完成，不一定交接
- 一个子任务结束，不一定交接
- 只有阶段闭环完成，或者出现决策边界，才交接

## 默认运行循环

Codex 默认应按以下循环运行：

1. 读取 `ops/charter.md`
2. 读取 `ops/workboard.md`
3. 读取最近的 `ops/handoff.md`
4. 选择最高优先级、且依赖已满足的工作项
5. 执行工作
6. 完成一个有意义子块后更新工作板
7. 在阶段完成前执行验证
8. 若验证未通过，继续修复
9. 若验证通过且阶段闭环，写入 `handoff.md`

## 交接类型

`handoff.md` 中交接类型应限制为：

- `phase-complete`
- `decision-required`
- `blocked`

## 为什么不能只用一个 handoff 文件

单个 `handoff.md` 无法同时稳定承载：

- 长期边界
- 当前工作
- 自动运行协议
- 最近交接状态

这会导致 Codex 虽然知道“最终要交接”，但不知道：

- 什么叫该继续
- 什么叫该验证
- 什么叫现在必须停

## 推荐配套 skill

为了让 Codex 真正遵守这套结构，建议增加一个项目级 skill：

- `kb-autonomous-run`

该 skill 的职责是：

- 在本仓库中自动任务默认先读 `ops/charter.md`、`ops/workboard.md`、`ops/handoff.md`
- 工作过程中按 `ops/runbook.md` 连续推进
- 仅在自然停止点写交接

## 实施范围

本次实施至少应包括：

- 创建 `ops/` 四个文件
- 创建 `kb-autonomous-run` skill
- 安装到 `.codex/skills/`
- 在 `wiki/INDEX.md` 和 `wiki/log.md` 中登记

## 成功标准

如果下次你对 Codex 说：

> 处理 workboard 里当前阶段的所有工作，直到自然交接点

那么它应能：

- 明确知道去哪里读工作和规则
- 知道不该在小完成点停下
- 知道必须做验证
- 知道什么时候该写 handoff 并停止
