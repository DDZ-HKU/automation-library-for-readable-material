# Agent 如何规划原子化 CLI 工具的使用，以及如何提升使用能力

日期：2026-04-13

## 结论

如果你已经把很多原子化 CLI 命令交给 agent，真正的问题就不再是“能不能调用命令”，而是两层更高的问题：

1. **agent 应该如何规划这些命令**
2. **agent 的工具使用能力如何持续升级**

最稳的答案可以压成一句话：

**先把 CLI 看成一组带副作用的原子动作，再把 agent 设计成一个“检索 -> 选择 -> 执行 -> 反馈 -> 复用”的闭环系统；能力提升则沿着 `tool use -> tool making -> tool library` 三层往上走。**

## 一、Agent 该怎样规划原子化 CLI

### 1. 不要让模型一开始就自由组合所有命令

原子命令很多时，LLM 最容易出现三类问题：

- 不知道先用哪个
- 会用，但顺序排错
- 同类命令过多时误检索

所以 planning 不该从“全部命令自由搜索”开始，而应从：

- 当前任务类型
- 当前状态
- 当前最可能需要的动作类别

开始。

也就是说，规划的第一层不是命令，而是**动作类型**。

例如先判定：

- 这是 `search`
- 还是 `transform`
- 还是 `execute`
- 还是 `verify`
- 还是 `handoff`

然后再在该类别内选具体 CLI。

### 2. 规划顺序应固定成一个闭环

对原子 CLI，最稳的规划 loop 通常是：

1. `retrieve`
2. `select`
3. `execute`
4. `observe`
5. `verify`
6. `continue or stop`

这里最关键的是：

- 命令调用不是单步行为
- 必须被环境反馈闭环约束

这和 ToolLLM 里的判断一致：

- tool use 不是一次 function call
- 而是一整条能力链

### 3. 把 CLI 先按“任务语义”分层

最实用的分法不是按技术类型，而是按 agent 任务语义：

- `search tools`
  - 例如 `rg`、`kb search`
- `state tools`
  - 例如 `git status`、`ops-phase-status`
- `build tools`
  - 例如编译、生成、转换
- `verify tools`
  - 例如测试、lint、校验脚本
- `control tools`
  - 例如 handoff readiness、continuation verification

这样 agent 在规划时先选类别，再选命令，误用率会低很多。

### 4. 默认先检索，后执行，最后验证

对原子 CLI 来说，最危险的不是“不会做”，而是“做得太快”。

所以默认顺序应是：

- 先用检索类命令缩小空间
- 再用执行类命令做最小动作
- 最后强制跑验证类命令

如果执行类命令先行，agent 就容易：

- 过早修改
- 误改
- 做了却没检验

### 5. 对副作用命令做显式边界

你不应该把所有 CLI 平权暴露给 agent。

应该明确区分：

- `read-only`
- `local-write`
- `high-cost`
- `destructive`
- `external-side-effect`

然后把这些边界放进 harness，而不是只靠 prompt 提醒。

## 二、有哪些常见范式

结合你刚补的这几篇工具论文，最有用的其实有五类范式。

### 范式 1：原子调用范式

适合：

- 探索
- 调试
- 临时问题

特点：

- 灵活
- 便宜
- 不稳定

它不是终点，只是起点。

### 范式 2：任务门面范式

把多个原子命令包成一个有语义的工具，例如：

- `scripts/kb`
- `scripts/ops-phase-status`
- `scripts/ops-check-handoff-readiness`

这是最推荐的主力范式。

原因：

- 降低检索负担
- 稳定输入输出
- 更容易让模型学会“何时调用”

### 范式 3：搜索式规划范式

这对应 ToolLLM / DFSDT 那类思路。

适合：

- 原子命令很多
- 可能有多条正确路径
- 需要回退和重选

特点：

- 不是单路径 ReAct
- 而是允许比较多条候选执行轨迹

### 范式 4：maker-user 分层范式

这对应 LATM。

高能力模型负责：

- 造脚本
- 造中层工具
- 提炼功能

低成本模型负责：

- 日常调用
- 组合使用

这是长期降成本最有效的模式之一。

### 范式 5：工具库聚合范式

这对应 ToolLibGen。

当中层脚本开始变多，新的瓶颈变成：

- 不知道该用哪个
- 同功能脚本重复
- 检索歧义

这时就不能继续平铺，而要：

- 聚类
- 聚合
- 提炼共享逻辑
- 组织结构化工具库

## 三、如何提升 agent 的工具使用能力

### 1. 先提升检索能力，不是先提升“调用数量”

Agent 变强的第一步，不是给更多命令，而是提高：

- 找到对的命令
- 排除不该用的命令

这意味着要优先建设：

- command metadata
- tool category
- retrieval helper
- examples

### 2. 让工具输出可被下游稳定消费

如果 CLI 输出：

- 太长
- 太噪
- 太不稳定

agent 就很难学会可靠使用它。

所以提升能力的关键手段之一是：

- 把原子 CLI 包成结构稳定的任务工具

### 3. 用“成功路径 + 失败路径”一起训练或评估

只告诉 agent：

- 什么时候该用命令

还不够。

也要告诉它：

- 什么时候不该用
- 哪类命令组合会失败
- 哪类中间结果意味着应回退

### 4. 提高能力靠的不是更长 prompt，而是更好的工具层

很多工具使用能力的提升，其实不是模型本身突然更强，而是：

- tool schema 更清楚
- 命令层级更清楚
- 检索更清楚
- 反馈更清楚

### 5. 能力提升最终会从“会调命令”转向“会管理工具资产”

这是这几篇论文最值得保留的判断。

当 agent 开始会：

- 用工具
- 造工具

新的瓶颈一定会上移到：

- tool organization
- retrieval quality
- cache strategy
- governance

## 四、给你一个最实用的落地顺序

### 第一步

保留原子 CLI，但只保留真正通用的基础命令。

### 第二步

把高频流程包成任务门面脚本。

### 第三步

给所有工具加：

- 类别
- 输入约束
- 输出约束
- 风险级别

### 第四步

引入 `maker-user` 分层，让高能力 agent 开始造工具。

### 第五步

当脚本开始变多，做 ToolLibGen 式的库化聚合。

## 一句话建议

如果你现在有很多原子化 CLI，最稳的路线不是继续把它们直接暴露给 agent，而是：

**把 agent 的使用能力先建在“任务门面 + 搜索式规划 + maker-user 分层”上，再把规模问题交给工具库聚合来解决。**
