# CLI 原子化聚合：管理者与架构师版

日期：2026-04-13

## 这份文档给谁看

这份版本面向：

- 技术负责人
- 架构师
- 需要决定“现在该不该聚合、先聚合哪层、怎么控制风险”的管理角色

它不讨论具体命令写法，而重点回答：

- 为什么 CLI 原子化之后还必须继续做聚合
- 聚合应分几层推进
- 每一层在解决什么管理问题
- 现在该投资源在哪一层

## 一句话结论

如果你已经把 CLI 做成很多原子命令，下一步最该管理的，不是“再加多少命令”，而是：

**如何把原子动作逐步提升成稳定任务入口，并在工具增多后建立治理层。**

换句话说：

**原子化解决的是可操作性，聚合解决的是可扩展性。**

## 一、为什么原子化之后还不够

把 CLI 原子化之后，团队通常会先得到短期收益：

- 命令更清楚
- 组合更灵活
- agent 更容易调用

但如果停在这里，长期会出现 4 个问题：

1. 检索成本上升
2. 误用率上升
3. 高频流程反复从零拼接
4. 工具越来越多，但没人知道该先用哪个

所以原子化不是终点，而是把复杂性从“命令内部”转移到“命令之间的选择与组织”。

## 二、你真正要管理的是 4 层，不是 1 层

### 1. Atomic Layer

这一层的职责是：

- 保留底层动作原语
- 提供灵活探索能力
- 作为未知场景下的保底接口

管理重点：

- 不要删掉原语层
- 但也不要让它长期承担主工作流

### 2. Facade Layer

这一层的职责是：

- 把高频任务从“命令组合”提升成“任务入口”

管理重点：

- 这是最值得优先投入的一层
- 因为它能最快降低误用率和检索成本

### 3. Planning Layer

这一层的职责是：

- 决定先调哪个工具
- 失败后如何回退
- 什么时候验证
- 什么时候停止

管理重点：

- 不要把所有稳定性问题都推给脚本
- 其中一部分必须由 route、planner、runbook 来承担

### 4. Governance Layer

这一层的职责是：

- 管理工具数量增长后的分类、聚类、统一接口和长期维护

管理重点：

- 当工具开始增多时，不再是“做更多脚本”的问题
- 而是“如何避免工具资产失控”的问题

## 三、最稳的投资顺序

如果你现在资源有限，最稳的投入顺序是：

1. 保留 atomic，不再继续无节制扩张
2. 先抽 5 到 10 个最高频 facade
3. 明确 facade 的输入、输出、失败边界
4. 让高能力 agent 或资深工程师负责造工具
5. 等工具量上来后，再进入 library/governance

不要一开始就投入“大一统平台化”，因为那通常会过早抽象。

## 四、什么时候说明你该升级到下一层

### 从 Atomic 升到 Facade

出现以下任意两项时：

- 某组命令高频重复
- 顺序稳定
- 输出需要标准化
- agent 经常选错
- 多个命令总是一起出现

### 从 Facade 升到 Governance

出现以下任意一项时：

- 名字相似但功能不同
- 功能重叠但名字不同
- agent 检索频繁误选
- 同类脚本持续增长
- 团队开始靠口头记忆哪个工具该怎么用

## 五、管理上最容易犯的错误

- 把原子化误当成体系建设完成
- 让低频命令也进入 facade，导致抽象污染
- 只加脚本，不治理命名和输入输出
- 工具已经明显增多，却还没有分类与元信息层
- 让普通 agent 长期手工拼高频动作链

## 六、你现在该怎么判断“先做哪一层”

可以直接问这 4 个问题：

1. 当前主要问题是命令不够，还是命令太难选？
2. 高频任务是否已经反复出现？
3. 失败更多来自命令能力不足，还是来自路由与误用？
4. 当前系统更缺 facade，还是更缺治理？

如果答案偏向：

- “太难选” -> 优先做 facade
- “经常走错” -> 优先补 planning
- “已经很多很乱” -> 优先做 governance

## 七、一句话行动建议

作为管理者或架构师，下一步不要继续追求“更多原子命令”，而应把目标改成：

**先把最常见的任务提升成 facade，再把工具增长问题前移为治理问题。**
