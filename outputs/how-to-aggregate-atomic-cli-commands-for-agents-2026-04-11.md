# 如何把原子化 CLI 命令聚合和组装给 Agent 使用

日期：2026-04-11

## 结论

如果你已经能把原子化 CLI 命令交给 agent 操作，那么下一步最重要的不是“继续加更多命令”，而是把这些命令提升成更高层的可复用单元。最稳的聚合方向通常有三层：

1. `atomic commands`
2. `task tools`
3. `tool libraries / tool assets`

对应到当前知识线：

- `ToolLLM` 告诉你如何让模型学会调用大量真实工具
- `LATM` 告诉你模型可以自己创造可复用工具
- `ToolLibGen` 告诉你工具一多，必须进入组织、聚类和聚合阶段

所以真正的问题不是“命令怎么串起来”，而是：

- 哪些命令应该保持原子
- 哪些应该被包装成中层任务工具
- 哪些应该再被整理成可检索的工具库

## 一、先分三层，不要直接把所有 CLI 扔给模型

### 1. 原子命令层

这层是最小动作：

- `rg`
- `ls`
- `sed`
- `git status`
- `pytest tests/x`
- `curl ...`

它们的特点是：

- 粒度小
- 语义单一
- 组合自由高
- 对模型要求高

适合：

- 探索
- 调试
- 临时查询

不适合：

- 长期复用
- 稳定工作流
- 大规模工具检索

### 2. 任务工具层

这层把多个原子命令包装成一个更高层动作，比如：

- `scripts/kb search <pattern>`
- `scripts/pdf-to-md <pdf>`
- `scripts/ops-check-handoff-readiness <project>`

特点是：

- 输入更少
- 输出更稳定
- 边界更清楚
- 更适合 agent 学会何时调用

这是最值得优先构造的一层。

### 3. 工具库层

这层不是再造新命令，而是管理一组工具：

- 按主题分组
- 按任务分组
- 按依赖关系分组
- 给出检索入口和聚合关系

这正是 `ToolLibGen` 那类工作在解决的问题：

- 工具一旦多起来，真正瓶颈会从“如何调用”变成“如何组织和检索”

## 二、聚合原子 CLI 的四种常见范式

### 范式 1：流水线包装

把若干固定顺序的原子命令包装成一个脚本。

例如：

- 输入一个 PDF
- 自动转 Markdown
- 自动放到 `raw/sources`

优点：

- 最简单
- 最稳定
- 最适合高频重复动作

缺点：

- 适应性弱
- 不适合分支很多的任务

适用场景：

- 文件预处理
- 固定发布流程
- 固定校验流程

### 范式 2：任务门面

不是暴露一串 CLI，而是暴露一个有明确语义的门面命令。

例如：

- `scripts/kb search`
- `scripts/ops-phase-status`

这类门面把很多底层实现藏起来，只保留任务语义。

优点：

- agent 更容易学会什么时候用
- 减少参数空间
- 减少提示词负担

这是我最推荐的默认范式。

### 范式 3：maker-user 分层

这就是 `LATM` 的思路。

不是所有 CLI 都直接交给同一个 agent：

- 高能力 agent 负责“造工具”
- 低成本 agent 负责“用工具”

在 CLI 世界里，这意味着：

- 先让高能力 agent 把常见命令组合成脚本
- 再让普通 agent 日常调用这些脚本

优点：

- 长期成本低
- 工具会越来越贴合项目

### 范式 4：库化聚合

这就是 `ToolLibGen` 的思路。

当脚本和工具开始变多时，不要再平铺：

- 要按功能聚类
- 抽共享逻辑
- 合并重叠能力
- 给工具库建立清晰目录和检索方式

优点：

- 规模化之后不会乱
- agent 检索准确率更高

## 三、设计时最重要的判断标准

### 1. 看“是否稳定复现”

如果一个命令组合经常重复，而且顺序稳定，就该升成脚本。

### 2. 看“是否需要模型自由度”

如果某步需要 agent 在很多路径里灵活选择，就保留原子。

如果不需要，就封装。

### 3. 看“输出是否能被稳定消费”

如果一个 CLI 输出不稳定、太噪、太长，agent 很难可靠接下一步。

这类命令应优先被包成结构更清晰的中层工具。

### 4. 看“是否已经出现检索成本”

一旦工具多到 agent 经常：

- 不知道该用哪个
- 误用相似工具
- 重复造轮子

就说明该进入 ToolLibGen 式的工具库管理阶段了。

## 四、最推荐的实际落地顺序

### 第一步

保留原子 CLI，但只保留真正通用的基础动作。

### 第二步

把高频工作流包成项目脚本。

例如：

- 知识检索
- handoff 校验
- PDF 预处理

### 第三步

给这些脚本建立主题目录和命名规范。

### 第四步

当数量上来后，开始做工具库聚类与聚合。

也就是：

- 搜索类
- 校验类
- 预处理类
- 发布类
- 运行控制类

## 五、一句话建议

不要让 agent 长期直接面对一堆原子 CLI。  
最稳的路线是：

**原子命令保底，任务门面做主力，maker-user 分层做演化，工具库聚合做规模化。**
